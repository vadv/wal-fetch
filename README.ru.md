# wal-fetch

Получает WAL-файлы и файлы истории таймлайнов с первичного сервера PostgreSQL для `restore_command` от имени роли с правом `REPLICATION`.

Первый вызов запускает локальный сервер на Unix-сокете, повторные вызовы переиспользуют его соединение с PostgreSQL.

[English](README.md)

## Как это работает

Каждый вызов `restore_command` запускает короткоживущий клиент. Первый клиент запускает фоновый процесс сервера, по одному на каталог PGDATA, остальные клиенты обращаются к нему через Unix-сокет. Между запросами сервер держит одно долгоживущее соединение с PostgreSQL и временный слот.

### Запуск

Клиент подключается к `<pgdata>/.wal-fetch/server.sock`. Если никто не отвечает, клиент захватывает эксклюзивный `flock` на `server.lock` и, как владелец блокировки, запускает сервер отдельным процессом в новой сессии, который наследует блокировку. Статус запуска передаётся через канал. Сервер завершается после `-idle-timeout` простоя, после чего блокировка достаётся следующему клиенту.

### Обработка запросов

Сервер принимает соединения по одному и не держит внутренней очереди: параллельные вызовы `restore_command` ждут в очереди ядра на сокете и обрабатываются последовательно. Клиент передаёт свой дедлайн вместе с каждым запросом. При ошибке запроса ничего не публикуется.

### Протокол (версия 1)

Построчный JSON поверх Unix-сокета, по одному соединению на запрос:

1. Клиент отправляет `{"version":1,"identity":"…","name":"000000010000000000000003","deadline":…}`.
2. Сервер отвечает `{"version":1,"ok":true,"length":16777216,"sha256":"…","id":"…"}`, затем передаёт ровно `length` байтов данных и закрывает свою половину соединения.
3. Клиент проверяет длину и SHA-256, записывает содержимое во временный файл в каталоге назначения, вызывает для него `fsync`, переименовывает в целевой файл и отвечает `{"version":1,"id":"…","published":true}`.
4. Позиция удержания слота продвигается только после этого подтверждения.

### Дайджест конфигурации

Каждый запрос несёт SHA-256 от эффективной конфигурации: параметров соединения с источником (хост, порт, пользователь, пароль, база данных, runtime-параметры), SSL-окружения, включая дайджесты файлов сертификатов, и всех рабочих опций. Секреты по сокету не передаются. При несовпадении дайджеста сервер отклоняет клиента с ошибкой `source configuration mismatch` вместо того, чтобы смешивать две конфигурации в одном процессе.

### Получение WAL

Для каждого сегмента сервер выполняет `IDENTIFY_SYSTEM`, сверяет запрошенный таймлайн с полученной историей таймлайнов, вычисляет точный диапазон LSN из имени файла и `-wal-segment-size` и принимает этот диапазон через `START_REPLICATION PHYSICAL`. Контролируется непрерывность передаваемых данных, данные усечены до размера сегмента: активный сегмент дополняется нулями до конца. Ответы истории таймлайнов ограничены 1 МиБ.

## Временный слот

Восстановление тратит время на воспроизведение файла до запроса следующего. Тем временем первичный сервер продолжает генерировать WAL и может переиспользовать (recycle) файлы, которые ещё нужны восстановлению. По умолчанию wal-fetch создаёт временный физический слот репликации, чтобы удерживать WAL между вызовами.

- **Имя:** `wal_fetch_` и 32 случайные шестнадцатеричные цифры в нижнем регистре; имя попадает в журнал сервера.
- **Время жизни:** создаётся при первом запросе WAL и существует, пока живо соединение сервера. PostgreSQL удаляет его, когда это соединение завершается или обрывается, в том числе при остановке сервера после `-idle-timeout`.
- **Удержание:** граница продвигается после доставки непрерывной последовательности файлов, сохраняется последний доставленный сегмент. Уже переиспользованные сервером файлы восстановить нельзя; WAL до момента создания слота также не защищён.

Используйте **`-no-slot`**, чтобы отключить создание слота, если удержание WAL обеспечивается другими средствами.

После **5 неудачных запросов WAL подряд без успешной публикации** wal-fetch освобождает слот и продолжает работу без создания нового. Как только WAL-файл опубликован и обмен репликации завершается успешно, следующий запрос может создать новый слот. Запросы истории на счётчик не влияют. Порог меняется опцией `-slot-failure-limit N`, значение `0` отключает его.

Ошибка PostgreSQL при чтении переиспользованного WAL освобождает слот немедленно. Порог учитывает и повторные локальные отклонения, например запрос сегмента из будущего. Замещающий слот не позволяет вернуть WAL, переиспользованный за время разрыва.

## Использование

Задайте параметры соединения в окружении сервиса PostgreSQL:

```sh
PGDATA=/var/lib/postgresql/data
PGHOST=leader
PGPORT=5432
PGUSER=replicator
PGPASSFILE=/var/lib/postgresql/.pgpass
PGSSLMODE=verify-full
```

Запись в passfile использует базу данных `replication`; права на файл должны быть `0600`.

```conf
restore_command = '/opt/wal-fetch "%f" "%p" || pgbackrest --stanza=main archive-get "%f" "%p"'
```

Без слота:

```sh
wal-fetch -no-slot -pgdata /var/lib/postgresql/data WAL_NAME DESTINATION
```

| Опция | По умолчанию | Назначение |
|---|---|---|
| `-h`, `-p`, `-U` | окружение PostgreSQL | Хост, порт и пользователь источника |
| `-pgdata` | `PGDATA` или текущий каталог | Каталог для Unix-сокета и журнала локального сервера |
| `-no-slot` | `false` | Получение без резервирования WAL |
| `-slot-failure-limit` | `5` | Число неудачных запросов WAL до приостановки создания слота; `0` отключает ограничение |
| `-log-file` | `<pgdata>/.wal-fetch/server.log` | Файл журнала сервера |
| `-syslog` | `false` | Также отправлять журнал сервера в локальный syslog |
| `-idle-timeout` | `5m` | Останавливать сервер после простоя |
| `-timeout` | `30s` | Таймаут запроса, включая ожидание в очереди |
| `-wal-segment-size` | `16MB` | Размер сегмента WAL на источнике; переопределите для кластера с нестандартным размером |
| `-serve` | `false` | Запустить сервер в foreground |
| `-version` | нет | Показать версию и выйти |

Изменение параметров соединения, слота или журналирования требует перезапуска локального сервера. Остановите его командой `kill -TERM "$(cat "$PGDATA/.wal-fetch/server.pid")"`; следующий запрос запустит его снова.

Для отладки можно запустить сервер в foreground; он принимает те же опции, кроме `WAL_NAME DESTINATION`:

```sh
wal-fetch -serve -pgdata /var/lib/postgresql/data
```

Версия установленного бинарного файла:

```sh
wal-fetch -version
```

## Безопасность

Все данные сервера лежат в каталоге `<pgdata>/.wal-fetch`, который создаётся с режимом `0700` от имени пользователя ОС PostgreSQL: `server.sock` (`0600`), `server.lock`, `server.pid` и `server.log`.

- Обе стороны проверяют пир Unix-сокета через `SO_PEERCRED` и закрывают соединения от чужого UID.
- Файлы блокировки и журнала открываются с `O_NOFOLLOW` и должны быть обычными файлами от имени того же UID с режимом `0600`; каталог сокета должен принадлежать этому UID и иметь режим `0700`.
- По сокету передаются только имена файлов, дайджесты и байты данных; параметры соединения участвуют только в дайджесте конфигурации.
- Целевой файл появляется через `rename` после `fsync`, поэтому PostgreSQL не увидит частичный сегмент или файл истории. При ошибке запроса целевой файл не меняется.
- Строки соединения с несколькими хостами отклоняются. Сервер фиксирует первые идентификатор системы и таймлайн и останавливается при их изменении.
- Оставшиеся файлы промежуточной записи (staging) удаляются при запуске владельцем блокировки. Ничего из предыдущего запуска не используется повторно.

## Журналы

События сервера по умолчанию попадают в `<pgdata>/.wal-fetch/server.log`: запуск и остановка, жизненный цикл слота, запросы файлов. Ошибки клиента уходят в stderr, который PostgreSQL захватывает при выполнении `restore_command`.

Чтобы использовать другой файл и дополнительно отправлять события в локальный syslog:

```conf
restore_command = '/opt/wal-fetch -log-file /var/log/postgresql/wal-fetch.log -syslog "%f" "%p" || pgbackrest --stanza=main archive-get "%f" "%p"'
```

Каталог журнала должен существовать и быть доступен для записи пользователю ОС PostgreSQL; файл должен принадлежать этому пользователю и иметь режим `0600`. Syslog использует метку `wal-fetch` и facility `daemon`; куда попадут сообщения, определяет настройка syslog на хосте.

Ротация журнала выполняется извне. Переименуйте файл и попросите работающий сервер переоткрыть его:

```sh
kill -USR1 "$(cat "$PGDATA/.wal-fetch/server.pid")"
```

Замена должна удовлетворять тем же правилам: обычный файл того же пользователя с режимом `0600`. При неудачном переоткрытии сервер продолжает писать в старый дескриптор и сообщает об этом в журнале.

## Устранение неполадок

Ошибки клиента уходят в stderr с префиксом `wal-fetch:`, и PostgreSQL сохраняет их для `restore_command`. Отклонения на стороне сервера клиент видит как `server rejected request: …`, а в `server.log` они записываются как `rejected error=…`.

| Сообщение | Причина | Действие |
|---|---|---|
| `source configuration mismatch` | Параметры клиента отличаются от параметров работающего сервера | Перезапустите сервер (см. «Использование») и повторите |
| `socket peer UID mismatch` | Пир сокета работает от другого пользователя ОС | Каталогом `$PGDATA` владеет один пользователь; проверьте, кто запустил другой сервер |
| `source system or timeline changed; start a new server` | Первичный сервер переинициализирован или перешёл на новый таймлайн | Сервер останавливается сам; следующий запрос запустит новый |
| `server startup failed` | Свежезапущенный сервер не смог стартовать | Читайте `server.log` |
| `PGDATA path is too long for Unix socket` | Путь длиннее 108 символов, предела для Unix-сокета | Используйте более короткий PGDATA |
| `server already running` | `-serve` в foreground при удержании блокировки другим сервером | Используйте работающий сервер или сначала остановите его |

Проверить временный слот можно через SQL; слот исчезает вместе с сервером-владельцем, что ожидаемо после `-idle-timeout` или `kill -TERM`:

```sql
SELECT slot_name, active, restart_lsn
FROM pg_replication_slots
WHERE slot_name LIKE 'wal_fetch_%';
```

## Ограничения

Только Linux. Сервер привязан к одному первичному серверу и таймлайну. Смена системы или таймлайна источника останавливает сервер; следующий запрос запустит новый против нового источника. При обрыве соединения теряется и удержание WAL временным слотом. Активный сегмент представляет собой снимок сброшенного WAL с нулевым хвостом.

Syslog требует локального приёмника на момент запуска. Доставка не гарантирована: приостановленный приёмник может потерять копии сообщений syslog; запись в файл продолжается. Ротация журнала выполняется извне: переименуйте файл и отправьте сигнал `SIGUSR1` процессу из `server.pid`; перезапуск не требуется.

## Сборка и тесты

Linux, Go 1.25. Тестам восстановления нужны Python 3, инструменты PostgreSQL 16 в `PATH` и непривилегированный пользователь.

```sh
go build -o wal-fetch .
go test ./...
python3 -m venv tests/integration/.venv
. tests/integration/.venv/bin/activate
python -m pip install -r tests/integration/requirements.txt
python -m pytest tests/integration -v
WAL_FETCH_TEST_SEGMENT_MB=1 python -m pytest tests/integration -v
```

Релизные сборки задают версию, которую печатает `-version`: `go build -ldflags "-X main.buildVersion=v1.0.0" -o wal-fetch .`

CI выполняет юнит-тесты, тесты с `-race` и vet, а также реальное восстановление с сегментами 16 МиБ и 1 МиБ, со слотом и без. Отдельная джоба прогоняет тот же integration-набор с бинарником, собранным с `-race`. Проверяются история таймлайнов, восстановление до целевой контрольной точки, жизненный цикл слота и обработка отказов.
