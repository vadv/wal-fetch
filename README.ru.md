# wal-fetch

Получает файлы WAL и истории таймлайнов с первичного сервера PostgreSQL для `restore_command` от имени роли с правом `REPLICATION`.

Восстановление запрашивает файл, воспроизводит его и только потом просит следующий. Пока оно воспроизводит, первичный сервер продолжает писать WAL и удаляет файлы, которые восстановлению ещё нужны. `wal-fetch` держит одно соединение и временный слот открытыми между запросами, поэтому эти файлы остаются доступны, когда за ними придёт восстановление.

Первый запрос запускает фоновый сервер на каждый PGDATA. Последующие запросы — короткоживущие клиенты, которые обращаются к нему через Unix-сокет в `<pgdata>/.wal-fetch/`.

## Быстрый старт

Параметры соединения берутся из окружения службы PostgreSQL:

```sh
PGDATA=/var/lib/postgresql/data
PGHOST=leader
PGPORT=5432
PGUSER=replicator
PGPASSFILE=/var/lib/postgresql/.pgpass
PGSSLMODE=verify-full
```

Запись в passfile использует базу данных `replication`, права на файл — `0600`.

```conf
restore_command = '/opt/wal-fetch "%f" "%p" || pgbackrest --stanza=main archive-get "%f" "%p"'
```

Без слота:

```sh
wal-fetch -no-slot -pgdata /var/lib/postgresql/data WAL_NAME DESTINATION
```

## Как это работает

### Запуск

Клиент подключается к `<pgdata>/.wal-fetch/server.sock`. Если никто не отвечает, он захватывает эксклюзивный `flock` на `server.lock` и, как владелец блокировки, запускает сервер отдельным процессом в новой сессии, который наследует блокировку. Статус запуска возвращается через канал. Сервер завершается после `-idle-timeout` простоя, и блокировка достаётся следующему клиенту.

### Обработка запросов

Сервер принимает соединения по одному и не держит внутренней очереди: параллельные запросы ждут в backlog сокета в ядре. Каждый запрос приносит свой deadline. Неудачный запрос ничего не публикует.

### Протокол (версия 1)

JSON по строкам, одно соединение на запрос:

1. Клиент отправляет `{"version":1,"identity":"…","name":"000000010000000000000003","deadline":…}`.
2. Сервер отвечает `{"version":1,"ok":true,"length":16777216,"sha256":"…","id":"…"}`, затем ровно `length` байт данных и half-close своей стороны.
3. Клиент проверяет длину и SHA-256, пишет цель через временный файл, делает `fsync`, переименовывает на место и отвечает `{"version":1,"id":"…","published":true}`.
4. Retention слота продвигается только после этого подтверждения.

### Дайджест конфигурации

Каждый запрос приносит SHA-256 дайджест действующей конфигурации: параметры соединения, SSL-переменные окружения, включая дайджесты файлов сертификатов, и поведенческие опции. Учётные данные по сокету не передаются. При несовпадении дайджеста сервер отклоняет клиента; два набора настроек в одном процессе не смешиваются.

### Чтение WAL

На каждый сегмент сервер выполняет `IDENTIFY_SYSTEM`, сверяет запрошенный таймлайн с полученной историей, вычисляет диапазон LSN из имени файла и `-wal-segment-size` и передаёт его через `START_REPLICATION PHYSICAL`. Непрерывность проверяется, данные обрезаются до размера сегмента, поэтому активный сегмент заканчивается хвостом из нулей. Ответы с историей таймлайнов ограничены 1 МиБ.

## Временный слот

По умолчанию сервер создаёт временный физический репликационный слот, чтобы сохранять WAL между запросами.

- **Имя:** `wal_fetch_` и 32 случайных шестнадцатеричных цифр в нижнем регистре; записывается в журнал сервера.
- **Время жизни:** создаётся при первом запросе WAL и удерживается соединением сервера. PostgreSQL удаляет его, когда это соединение закрывается или теряется, включая остановку сервера после `-idle-timeout`.
- **Retention:** продвигается после доставки непрерывных файлов и сохраняет последний доставленный сегмент. Уже удалённые файлы слот не вернёт, и WAL, записанный до создания слота, он не защищает.

`-no-slot` отключает создание слота, если retention управляется другими средствами — например pgBackRest или `wal_keep_size`.

После 5 неудачных запросов WAL без успешной публикации слот освобождается и новый не создаётся. Как только файл WAL опубликован и обмен по репликации завершился успешно, следующий запрос WAL может создать слот снова. Запросы истории счётчик не меняют. `-slot-failure-limit N` меняет порог, `0` отключает его.

Ошибка PostgreSQL при чтении удалённого WAL освобождает слот сразу. Порог также покрывает повторяющиеся локальные отказы, например запрос будущего сегмента. Новый слот не восстановит WAL, удалённый за время паузы.

## Параметры

| Опция | По умолчанию | Назначение |
|---|---|---|
| `-h`, `-p`, `-U` | окружение PostgreSQL | Хост, порт и пользователь источника |
| `-pgdata` | `PGDATA` или текущий каталог | Каталог для Unix-сокета и журнала локального сервера |
| `-no-slot` | `false` | Получение без резервирования WAL |
| `-slot-failure-limit` | `5` | Число неудачных запросов WAL до приостановки создания слота; `0` отключает ограничение |
| `-log-file` | `<pgdata>/.wal-fetch/server.log` | Файл журнала сервера |
| `-syslog` | `false` | Также отправлять журнал сервера в локальный syslog |
| `-idle-timeout` | `5m` | Останавливать сервер после простоя |
| `-timeout` | `30s` | Таймаут запроса, включая ожидание в очереди |
| `-wal-segment-size` | `16MB` | Размер сегмента WAL на источнике; переопределите для кластера с нестандартным размером |
| `-serve` | `false` | Запустить сервер в foreground |
| `-version` | нет | Показать версию и выйти |

Изменение параметров соединения, слота или журналирования требует перезапуска локального сервера:

```sh
kill -TERM "$(cat "$PGDATA/.wal-fetch/server.pid")"
```

Следующий запрос запустит его снова. Для отладки сервер запускается в foreground с теми же опциями, без `WAL_NAME DESTINATION`:

```sh
wal-fetch -serve -pgdata /var/lib/postgresql/data
```

## Журнал

События сервера пишутся в `<pgdata>/.wal-fetch/server.log`: запуск, остановка, жизненный цикл слота, запросы файлов. Ошибки клиента идут в stderr, который PostgreSQL собирает при выполнении `restore_command`.

```conf
restore_command = '/opt/wal-fetch -log-file /var/log/postgresql/wal-fetch.log -syslog "%f" "%p" || pgbackrest --stanza=main archive-get "%f" "%p"'
```

Каталог журнала должен существовать и быть доступен для записи пользователю ОС PostgreSQL; файл должен принадлежать ему с правами `0600`. Syslog использует тег `wal-fetch`, facility `daemon`, и пишет туда, куда настроен syslog на хосте.

### Ротация

Ротация внешняя. Переименуйте файл и попросите работающий сервер открыть его заново:

```sh
kill -USR1 "$(cat "$PGDATA/.wal-fetch/server.pid")"
```

Новый файл должен удовлетворять тем же правилам: обычный файл, тот же владелец, права `0600`, поэтому logrotate нуждается в `create 0600 postgres postgres`. Неудачное повторное открытие оставляет старый дескриптор и записывается в журнал.

```conf
/var/log/postgresql/wal-fetch.log {
    daily
    rotate 14
    create 0600 postgres postgres
    postrotate
        pid=/var/lib/postgresql/data/.wal-fetch/server.pid
        if [ -f "$pid" ] && kill -0 "$(cat "$pid")" 2>/dev/null; then
            kill -USR1 "$(cat "$pid")"
        fi
    endpostrotate
}
```

Проверяйте, что PID жив, прежде чем отправлять сигнал: `server.pid` удаляется при остановке сервера, а оставшийся PID мог уже достаться другому процессу. Когда сервер не работает, hook ничего не делает: следующий запрос запустит сервер, который откроет новый файл.

`copytruncate` работает без сигнала, потому что сервер продолжает писать в тот же дескриптор, но поддерживаемый путь — переименование плюс `SIGUSR1`. Вывод, полученный сервером при запуске (stdout и stderr, для ошибок запуска и паник), продолжает попадать в ротированный файл.

## Безопасность

Все данные сервера лежат в каталоге `<pgdata>/.wal-fetch` с правами `0700` от имени пользователя ОС PostgreSQL: `server.sock` (`0600`), `server.lock`, `server.pid` и `server.log`.

- Обе стороны проверяют пир Unix-сокета через `SO_PEERCRED` и закрывают соединения от чужого UID.
- Файлы блокировки и журнала открываются с `O_NOFOLLOW` и должны быть обычными файлами того же UID с правами `0600`; каталог сокета должен принадлежать этому UID и иметь права `0700`.
- По сокету передаются только имена файлов, дайджесты и байты данных; параметры соединения участвуют только в дайджесте конфигурации.
- Целевой файл появляется через `rename` после `fsync`, поэтому PostgreSQL не увидит частичный сегмент или файл истории. При ошибке запроса целевой файл не меняется.
- Строки соединения с несколькими хостами отклоняются. Работающий сервер фиксирует идентификатор системы источника и отклоняет другой кластер. Смена таймлайна того же кластера перезапускает сервер.
- Оставшиеся файлы промежуточной записи удаляются при запуске владельцем блокировки; ничего из предыдущего запуска не используется повторно.

## Диагностика

Ошибки клиента пишутся в stderr с префиксом `wal-fetch:`. Отказы сервера видны на клиенте как `server rejected request: …` и в `server.log` как `rejected error=…`.

| Сообщение | Причина | Что делать |
|---|---|---|
| `source configuration mismatch` | Настройки клиента отличаются от настроек работающего сервера | Перезапустить сервер и повторить |
| `socket peer UID mismatch` | Пир сокета работает под другим пользователем ОС | `$PGDATA` принадлежит одному пользователю; проверьте, кто запустил второй сервер |
| `source system identifier changed` | По адресу источника теперь находится другой кластер | Проверить адрес источника; ошибка запроса позволяет обратиться к архиву |
| `source system or timeline changed; start a new server` | Тот же кластер перешёл на новый таймлайн | Сервер перезапускается автоматически |
| `server startup failed` | Только что запущенный сервер не поднялся | Читайте `server.log` |
| `PGDATA path is too long for Unix socket` | Путь длиннее ограничения Unix-сокета в 108 символов | Используйте более короткий PGDATA |
| `server already running` | `-serve` в foreground, когда блокировку держит другой сервер | Работайте через существующий сервер или остановите его |

Временный слот исчезает, когда его сервер завершается, — это ожидаемо после `-idle-timeout` или `kill -TERM`:

```sql
SELECT slot_name, active, restart_lsn
FROM pg_replication_slots
WHERE slot_name LIKE 'wal_fetch_%';
```

## Ограничения

Только Linux. Потеря соединения сервера означает потерю удержания WAL слотом. Активный сегмент — это снимок записанного WAL с хвостом из нулей.

Syslog требует локального получателя на момент запуска. Доставка best effort: зависший получатель может потерять копии в syslog, файловый журнал продолжает писаться.

## Сборка и тесты

Linux, Go 1.25. Тесты восстановления требуют Python 3, утилиты PostgreSQL 16 или 18 в `PATH` и не-root пользователя.

```sh
go build -o wal-fetch .
go test ./...
python3 -m venv tests/integration/.venv
. tests/integration/.venv/bin/activate
python -m pip install -r tests/integration/requirements.txt
python -m pytest tests/integration -v
WAL_FETCH_TEST_SEGMENT_MB=1 python -m pytest tests/integration -v
```

При утилитах PostgreSQL 18 в `PATH` задайте `WAL_FETCH_TEST_PG_VERSION=18` при запуске pytest.

Релизная сборка задаёт версию, которую показывает `-version`:

```sh
go build -ldflags "-X main.buildVersion=v1.0.0" -o wal-fetch .
```

Сборка из исходников показывает `dev`.

CI выполняет проверки unit, race и vet, а также реальное восстановление с сегментами 16 МиБ и 1 МиБ, со слотом и без. Отдельная задача прогоняет тот же интеграционный набор против бинарника, собранного с `-race`. Проверяются история таймлайнов, восстановление до целевой контрольной точки, жизненный цикл слота и обработка отказов.
